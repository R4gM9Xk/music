## 三、量化验收（本轮改动的关键断言）

### 1. 封面尺寸 —— PASS，与代码推导分毫不差

代码推导：`min(stageW × 0.82, …)`，411.4dp 屏 → 期望 **337dp**。

截图像素测量（3 条独立水平线，y=750/800/850）：
```
封面左缘 = 130px (9.0%)   右缘 = 1311px (91.0%)
宽度 = 1181px = 82.0% 屏宽 = 337dp
左留白 37dp / 右留白 37dp（完全对称）
```
**期望 82.0% / 337dp，实测 82.0% / 337dp —— 精确吻合。**

对比真机反馈前的旧值：旧算法同屏算出 371dp（90% 屏宽），现值 337dp，收窄 34dp，两侧各多出 37dp 呼吸。

### 2. 控制行对齐 —— PASS，对称偏差 0.07pp

取自 `uiautomator` 的控件真实 bounds（非像素亮块，避免图标字形干扰）：

| 控件 | bounds | 中心占屏宽 |
|---|---|---|
| 播放模式 | [268,2704][394,2872] | 23.0% |
| 上一首 | [394,2704][562,2872] | 33.2% |
| **播放键** | （66dp，像素亮块实测） | **49.6%** |
| 下一首 | [877,2704][1045,2872] | 66.7% |

- 播放键中心 **49.6%**，偏差 0.42pp（阈值 2pp）→ **PASS**
- 上一首/下一首关于中心对称偏差 **+0.07pp** → **PASS**

对比修复前的实测值（`SpaceBetween` 布局）：模式钮 13.8% / 上一首 29% / 播放 50% / 下一首 71%，左右不对称。**修复确认生效。**

> 测量方法说明：初次用像素亮块中心判定 symmetry 得 FAIL(2.92pp)，排查发现是**图标字形本身不对称**（Prev 实心三角偏左、Next 偏右），像素亮块中心 ≠ 控件几何中心。改用 uiautomator bounds 后 PASS。这个坑记下来，后续验收用 bounds 不要用亮块。

### 3. 播放模式四态 —— 4/4 各不相同

对每次点击后的截图，在模式钮区域做 6×6 亮像素网格指纹：

| tap | 总亮像素 | 判定 |
|---|---|---|
| 1 | 704 | 不同 |
| 2 | 837 | 不同 |
| 3 | 722 | 不同 |
| 4 | 468 | 不同 |

**四档全部不同（4/4）**，且截图目视确认：
- 顺序播放：单箭头无环、**无强调色**（非默认态才高亮，符合设计）
- 单曲循环：环 + 中央 `1`、**青色高亮**
- 列表循环 / 随机：各自轮廓 + 高亮

### 4. 可访问性 —— 修正确认

## 五、发现的问题（均未修改代码，按要求仅记录）

### 1. 【既有·已知】搜索空态是裸文本，未接入空态三件套

搜索无结果时显示一行居中文字「没有找到「zzzzlost」相关内容」，**无图标、无 CTA**，与已接入三件套的曲库五 tab 不一致。

这不是本轮遗漏：上一轮 `empty-state` 任务的作用域明确限定为「曲库五 tab + 歌单空卡」，搜索屏被列为「只记录不修改，由 Lead 决定下一轮」。本轮实测确认该缺口仍在。

**建议**：下轮把搜索空态接入 `GlassEmptyState`（图标用 `GlassIcons.Search`，标题「没有找到相关内容」，副标题带关键词，无 CTA 或「清空搜索」CTA）。

### 2. 【既有·本轮新发现】行内下拉的浮层透字

下拉列表展开时，其玻璃面板透明度偏高，**下层设置行文字（「动效强度」等）透上来与列表项文字重叠**，可读性受损。

原因可定位：`SettingDropdown` 的 `GlassSurface(level = GlassLevel.Hi)` **没有传 `scrim`**。而本项目既有结论（`chromeScrim` 的整套 KDoc）正是「haze blur 生效 ≠ 透字不可辨，必须靠 scrim 压对比」。下拉浮层是**任意内容之上**的浮层，比 chrome 更需要 scrim。

注意：模拟器 blur 走 SwiftShader 退化路径（零模糊），会放大这个问题；**真机上带上 blur 后可能好很多，但按既有推导，透字仍会保留可辨的残余**。

**建议**：给 `SettingDropdown` 的浮层传 `scrim = glass.chromeScrim`（或新开一档浮层专用 scrim）。这是一行改动，但本轮按"非必要不动代码"未做。

### 3. 【环境·非缺陷】性能数据不可用于真机判断

```
Total frames 1270 / Janky 1269 (99.92%)
50th percentile: 150ms
```

**这是模拟器 SwiftShader 软件渲染的固有表现**，不是应用性能问题——此前多轮模拟器测试都有同样现象（`ro.hardware.egl=emulation`）。真机（一加 13，adreno）上一轮实测为 **0.35% 掉帧 / 11842 帧**。

**本项不构成应用缺陷，但也不能用来证明性能**，如实标注。

## 六、必须真机验证的遗留项

1. **游戏助手音乐卡片是否出现**（模拟器无厂商游戏助手）——`CATEGORY_APP_MUSIC` 是必要条件但不保证充分，ColorOS 可能另有白名单。若真机仍不出现，属厂商侧限制，App 侧无解法。
2. **行内下拉在真机 blur 生效环境下的透字程度**（§五.2）——决定要不要加 scrim。
3. **导航栏 `chromeScrimNav` 0.72 的实际透字可见度**——模型给的下限是 0.772，0.72 是刻意放宽，需真机确认列表文字没有变得可读。若可读，回退 0.76。
4. **蓝牙耳机媒体键**（MediaButtonReceiver 已注册，但实际响应需真机 + 蓝牙外设）。
