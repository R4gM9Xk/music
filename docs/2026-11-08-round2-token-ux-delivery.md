## 二、逐项实现要点

### ① S 间距 token 接线（§10.8 第 1 项）

**改前**：`object S` 定义完整但**全仓零引用**——117 处间距字面量各自裸写，同族缝隙出现 12/13/14 三种值。

**改后**：所有间距语义（`padding` / `Spacer` / `spacedBy` / 区块留白）一律读 `S.*`。

**关键裁定（写进 `S` 的 KDoc，这是本轮唯一新增的规则）**：

- **什么算间距**：`padding`、`Spacer` 宽高、`Arrangement.spacedBy`、区块之间留白。
- **什么不算**（保持裸值，三个类别）：
  1. **组件几何**——`.size/.width/.height` 宽高、图标尺寸。这是「元件多大」而非「隔多远」，混进刻度会让刻度失去语义；
  2. **微缝豁免 0–6dp**——图标-标签缝、胶囊内光学 padding；
  3. **几何推导量**——封面边长公式、飞行端点偏移、空态顶部定位等由布局算式推出的中间值。
- **刻度外值归位口径**：就近取刻度；正中间取「让留白不缩小」的一档（宁可松不可挤）。7→8、9→8、10→12、13→12、15→16、28→24、30→32、34→32；14 与 18 按语义二分（行内缝 vs 区块留白）。
- 每个偏离直觉的归位点都写了行内注释说明为何选这档——否则下一个人看到 `16.dp` 会以为是随手写的。

**新增 `S.Gap20 = 20`**，`PageMargin` 改为 `= Gap20`（保留语义别名但不另写一个 20：两份 20 就是两个真相）。

**三个真实观感变化**（如实记录，是「一致性优先」的取舍）：
- 迷你条/面板/列表行内边距 15/14/13 → 16/12/12（同族收敛）
- 部分区块留白 14 → 16、18 → 20（向上取，留白变松一档）
- `搜索空态顶部 56dp` **刻意不归位**：它不是段落间距而是把一行字推到视觉中心的一次性几何量，就近取 32 会读成「列表第一行」而不是「没有结果」

### ② A3 取色公式归一（§10.8 第 2 项）

**改前**：三套公式并存——手调预设 `GlassPalettes`、自定义色 `fromSeed`、封面 `paletteFromBitmap`（系数与 `fromSeed` 完全不同）。同一色相在三条路径下有三种深浅，切歌时氛围会跳。

**改后**：`paletteFromBitmap` **只负责从位图提取一个 seed**，派生一律走 `AuroraPalette.fromSeed`。

**系数全部重拟合**（对齐 4 个手调预设 × 4 个派生字段 = 16 色点，CIEDE2000 最小二乘）：

| 指标 | 改前 | 改后 |
|---|---|---|
| RMS ΔE00 | 5.05 | **1.28**（降 74.6%） |
| 最差 ΔE00 | 9.04（Coral.seed3） | **2.63**（Teal.deep） |

ΔE00 口径已写死进 KDoc：sRGB 逆伽马阈 0.04045 → D65 标准矩阵（逐行列出系数）→ 白点 (0.95047, 1, 1.08883) → f(t) 阈 (6/29)³；kL=kC=kH=1 含 RT 项；**RMS 分母 = 16**（seed 本身是恒等输入，不计入）。单测同口径输出 1.256/2.504，差异仅浮点末位。

**三路径一致性（靛紫 #7F77DD 实测）**：

| 路径 | seed2 | seed3 | deep | deep2 |
|---|---|---|---|---|
| A 品牌预设（手调基准） | #AFA9EC | #CECBF6 | #241C4A | #0E0A20 |
| B 用户手选 → fromSeed | #B1ACED | #CFCCF5 | #1B1842 | #07051C |
| C 封面恰好取到 → fromSeed | #B1ACED | #CFCCF5 | #1B1842 | #07051C |

**B 与 C 逐位相同**（同一纯函数、同一输入的两次调用）；A vs B 残差 ΔE00 ≤ 2.08，低于常规可辨阈值 3.0。

**顺带修掉一个既有 bug**：旧式 `(s*1.05f).coerceAtLeast(0.35f)` 会给灰/白/黑封面 swatch（s≈0）**强行注入 0.35 饱和**，配 deep 的低明度 → 中性封面的极光底被染成**暗红色**（实测灰 seed 旧 deep = `#140D0D`，改后 = `#262626` 纯灰）。新门控 `g = clamp((s-0.05)/0.20, 0, 1)`：s≤0.05 不注入、s≥0.25 完全线性（不影响拟合）、中间线性过渡。已加回归单测（断言灰/白/黑 seed 的 R/G/B 通道最大差 < 0.002）。

**明确结论：不需要保留手调覆盖表**——16 色点全部 ΔE00 ≤ 2.63；给单个预设开特例会重新引入公式跳变，那正是 A3 要治的病。`GlassPalettes` 保留但**降级为校准基准**（运行时不再作为派生路径）。

**注意一个技术前提**：`fromSeed` 改成**纯 Kotlin RGB↔HSV**（逐位对齐 `android.graphics.Color` 算法）。两个理由：① 配色数学不该依赖 Android 平台，`fromSeed` 因此可在任意线程调用；② `core:ui` 的 JVM 单测没开 `isReturnDefaultValues`，`colorToHSV` 会抛 "not mocked"。
⚠️ **不要**为了让旧实现能测而加 `isReturnDefaultValues = true` —— 它会让 `colorToHSV` 静默返回全 0 数组，把**所有 seed 变成黑色**，错误被吞掉比抛异常难查得多。这条理由已写进 KDoc 防止后人「顺手加上」。

### ③ 播放页歌名出卡 + 封面放大（§10.8 第 3 项）

**改前**：歌名 16sp 埋在玻璃控制台内部；封面 `min(280dp, …)` 硬上限。

**改后**：
- **歌名组出卡**：歌名/副标题成为卡外**裸内容**（无容器、无描边、无底色），与封面共享同一片背景。论证写进 KDoc：卡片是**容器**，容器内元素天然读作「容器的一个字段」；歌名在卡里时与进度条、收藏钮同级，切断了「封面 ⇄ 歌名」这条唯一的归属关系。
- **封面放大**：取消 280dp 硬上限，改「宽度导向 + 边缘留白」推导；**仍保持 `封面边长 ≤ min(stageW, stageH)`** 这条硬约束（横屏曾因 `coerceAtLeast(96dp)` 造出椭圆，见 PlayerScreen.kt:307-313 的血泪注释）。
- **控制台瘦身**：只留进度/时间/控制键，高度从 202dp 收到 152dp。
- **飞行系统同步**：`PlayerFlightOverlay` 的两个不能自动跟随的点已处理——① 替身字号/行高插值终点改成新真身（歌名 16sp→20sp Bold、行高 22→26）；② 歌名出卡后不再是卡的子节点，透明度改自己用 `sharedAlpha`（= playerSharedAlpha × sheetAlpha），否则退出飞行时会比别的元素晚 300ms 硬消失。

**飞行健壮性未动**：`trackFlight` 16 处引用、F4 几何闸门、`keepOnDispose`、`waitForRects` 超时回退、`visualMode==Lyrics` 时封面不飞的既有行为全部保留。

### ④ 空态三件套（§10.8 第 4 项）

新建 `core/ui/.../components/EmptyState.kt`（392 行）：**图标（弱）/ 标题（主）/ CTA（唯一可点，明确形状）** 三件套 + 可选副标题。

**接入三处**：
- 曲库五 tab（专辑/艺术家/文件夹/流派/歌单）各给**语义化图标**，不再五个 tab 同一个图标；
- 权限被拒档：**保留「去授权」CTA**（应用内唯一授权入口，历史审计明确不可移除），且与「库里真没歌」在图标/标题/CTA 三处都不同；
- 歌单空卡：0 首歌的卡片改为**小图标 + 「去添加歌曲」胶囊**（模拟器实测截图见下），卡片点击行为不变。

**可访问性**：整体语义合并，标题只朗读一次；CTA 有 `role = Role.Button`、可聚焦。

### ⑤ 播放模式合并按钮（用户新增，QQ 音乐同款）★

**改前**：随机（开/关二态）与循环（Off/All/One）是两个独立图标钮，单曲循环额外画 6dp 角标。

**改后**：**一枚四态按钮**，顺序播放 → 列表循环 → 单曲循环 → 随机播放 → 循环。

**合并理由**（写进 KDoc）：两个控件在语义上是正交开关，但在用户心智上只有一个问题——「这首歌放完怎么办」。两个控件同时亮着时，用户要先把两个状态在心里组合一次才知道会发生什么：`随机 + 单曲循环 = ?`（答案：单曲循环赢、随机不生效——这个优先级规则在任何 UI 上都没被表达过）。合并后「当前模式」成为一个可命名的单一状态，一次点击遍历，不再有隐藏优先级。
**代价**是牺牲了「随机 + 单曲循环」这个组合——有意取舍，依据是它本身无意义（随机一首再无限重复它）。

**四态 ⇄ 持久化字段映射**（字段名与语义**一字未改**）：

| 视觉态 | shuffleOn | repeatMode | restore 读法 |
|---|---|---|---|
| 顺序播放 | false | Off | shuffle=false 且 repeat=Off |
| 列表循环 | false | All | shuffle=false 且 repeat=All |
| 单曲循环 | false | One | shuffle=false 且 repeat=One |
| 随机播放 | true | All | **只看 shuffleOn**（true 即随机） |

`shuffleOn = true` 时**忽略** repeatMode —— 这条容错让旧快照/其它入口产生的「随机+Off」「随机+One」也稳定显示成「随机播放」，不会出现「按钮显示顺序播放、实际却在随机」的错位。

派生收敛在 `AppState.cyclePlayMode()`（一次进入、一次下发、一次存盘），UI 不做两次调用拼接（否则中途重组会看到半迁移状态，且一次点击写两次盘）。

**动效三层**（用户明确要求）：
1. **图标形变**：`AnimatedContent` 交叉过渡——旧图标淡出 + 缩到 0.72 + 逆时针转 90°，新图标反向淡入转正。90° 而非 180°：180° 读作「翻了个面」，与「向前走一档」的运动方向相反。**旋转按各子树自己的进出进度推**（不是 transition 统一旋转），于是读作「旧的一枚转走、新的一枚转进来」。
2. **强调色环脉冲**：切换瞬间从图标位置扩散淡出，即时回执。
3. **模式标签**：1.2s 后消失的四态中文名，承载「列表循环」这种纯图标无法区分的语义。

三个动画的 alpha/旋转/缩放**全部写在 `graphicsLayer` 的 lambda 里（绘制期读）**，不产生逐帧重组；时长曲线走既有 `GlassMotion.tweenPress`/`tweenHover`，自动被「动效强度」三档乘过。

**标签落点**（实测选的方案）：放在**底部 hint 行**，不是按钮旁浮层。理由：hint 行本来就是「恒定一行、恒定高度、可换文案」的既有契约（它为「不出字也要占位」设计的），标签只是又一个消费者；浮层会顶飞 `SpaceBetween` 那一行的配重。优先级：模式标签 > 操作提示（瞬态反馈必须压过常驻教学）。

**新图标四枚**（`GlassIcons` 末尾追加，1.8/1.9 笔画、24 viewBox）：`PlayOrder` / `PlayListLoop` / `PlayRepeatOne` / `PlayShuffle`。
- 为什么是四枚独立图标而非两枚拼装：四态里三态长得很像（只在箭头与角标上差一点），20dp 下几乎不可辨；四枚独立图标把状态编码进**整体轮廓**，这是小尺寸下唯一可靠的区分维度。
- `PlayOrder` **无环**——其它三态都带循环箭头，只有它不带，「有没有环」本身就是一档信号。
- `PlayRepeatOne` 把 `1` 画进环心，而非再叠角标（6dp 角标在 20dp 图标上会被压成半颗像素，且与「未读点」语义撞车）。
- 旧 `Repeat`/`Shuffle` 保留（面板/其它入口可能引用），KDoc 写明「不要再与 `PlayListLoop` 同屏出现」。

**可访问性（本轮实测修出来的真实缺陷）**：初版把 `semantics{}` 与 `clickable{}` 分列在内外两层，`adb shell uiautomator dump` 证实生成了**分裂结构**——`content-desc="播放模式"` 的节点 `clickable="false"`，旁边还有个 `clickable="true"` 的空标签节点，读屏能念出名字却没有「双击激活」动作。
三次尝试才修对（记录在代码注释里避免后人重犯）：
- ① `semantics then clickable` → 标签与点击性分裂到两个节点；
- ② `clickable then semantics`（`ConsoleIcon` 的写法）单独看没问题，但本按钮内层是 `AnimatedContent`，它给进出两个图标各建了语义节点，外层被识别成**容器**，仍然分裂；
- ③ `semantics(mergeDescendants = true)` → 被两个过渡子树干扰，结果不稳定；
- ✅ **最终解 `clearAndSetSemantics`**：丢弃整个子树的语义再由这里重建一个节点。图标本来就是 `contentDescription=null` 的纯装饰，过渡节点也不是给读屏用的，全丢正是想要的。
实测确认：`class="android.widget.Button" content-desc="播放模式" clickable="true"` —— 单一节点、可点击、role 正确。

### ⑥ 玻璃透字「改用高斯模糊」——定量否决（用户新增）

用户问：「玻璃部件下方信息穿透，能否改为加高斯模糊解决」。**结论：不可行**，且这不是定性判断——模型用真机两个实测锚点标定，能复现**全部**已发布数据点：

| 表面 | 模型复算 | 真机实测 |
|---|---|---|
| 迷你条 r=26dp/tint 0.16 | **4.30:1** | 4.3:1 ✅ |
| 导航栏 r=20dp/tint 0.10 | **11.33:1** | 11.4:1 ✅ |
| +scrim 0.80 | 1.40 / 1.80 | 带 1.1–1.8 ✅ |

**三项独立论证，任一条都足以封死**：

**A. 高斯模糊保均值 → 不可约下界。** 透字不是一个标量而是一条调制带：高频（笔画形状，blur 能衰减）+ 低频（整行文字整体提亮，blur **完全不能**改变）。半径推到 ∞（糊成平色场）的下界：迷你条 **1.40→1.20**、导航栏 **1.80→1.33**。花无穷大 GPU 代价买 0.2–0.5；而 scrim +0.06（零 GPU 成本）就能把迷你条拉到 1.25。

**B. 残幅 ∝ 1/r，线性增益。** 一维矩形笔画与高斯核卷积 `m(σ)=erf(w/(2√2σ))`，σ≫w 时 `m ∝ 1/σ ∝ 1/r`。实测反解迷你条 m=0.547 → σ_eff≈7px（≈2dp@560dpi，与「14–29px 边缘过渡」自洽）。要让 m 降到 0.1 需 **r≈155dp（现值 6 倍）**。半径翻倍只砍一半残值。

**C. 退化路径是封口条件（决定性）。** 无 RenderEffect 时 haze 走 `ScrimBlurEffect` → **半径完全不影响像素**，「加大 blur」收益 = 0 而「降 scrim」代价 100% 兑现。反解退化路径守 2:1：迷你条 a≥0.761、导航栏 **a≥0.772** → scrim 最多只能 0.80→0.78，而 0.78 在 blur 生效时只买回 0.04（1.40→1.44），肉眼不可辨。**⇒ 可行域宽度 ≈ 0。**

**可行域扫描（c≤1.5，深色）**：

| scrim | 迷你条需 r | ×现 | 导航栏需 r | ×现 | 判定 |
|---|---|---|---|---|---|
| 0.80 | 18.5dp | 0.71× | 49.3dp | 2.47× | ✅ 现状达标 |
| 0.74 | 34.8dp | 1.34× | **455dp** | **22.8×** | ❌ 整屏模糊 |
| 0.70 | 56.7dp | 2.18× | 下界 1.58>1.5 | — | ❌ 无解 |
| ≤0.65 | 下界已>1.5 | — | 同 | — | ❌ 数学无解 |

**落地决策：不改任何数值**（按「不可行则不硬改」分支）。深色 `chromeScrim` 保持 `#1A1A24@0.80`、浅色 `#F2F2F6@0.74`、blur 保持 26/20/12dp。
但把原来那句**没有数学支撑的断言**（「scrim alpha 已达 0.80，模糊贡献只剩 20%，加大半径肉眼不可辨」——当年是从 scrim 倒推的）**全部换成了可复算的推导**，分布在 4 个文件的 KDoc 里。这类断言在代码库里是负债。

**GPU 量级**（从 haze 1.6.10 AAR 反编译确认）：`Rect.inflate(blurRadiusPx)` 外扩采样层 + `createBlurEffect` 常数箱式两趟 1D 分解 → 净效应 **O(r²)**（面积 × 核长）。半径翻倍 ≈ 采样开销 ×4 × 核长 ×2 = **6–7×**。r=455dp 时采样层面积是条本体的 **>100 倍**，早已不是「一条导航栏」而是整屏毛玻璃。

**正确的方向已写进 KDoc 留给下一轮**：瓶颈是**低频项** → 解法在内容侧（列表滚到 chrome 下方前边缘渐隐），但必须先有**硬保证**（chrome 区域遮罩，而非依赖时序），否则 scrim 一降就破 2:1。

## 三、模拟器实测（模拟器 OnePlus13_API36 / Android 16 / 1440×3168@560dpi）

## 四、构建环境（本轮踩坑记录，供后人）

沙箱下 `~/.gradle`、`%LOCALAPPDATA%\kotlin`、`C:\Users\a\.android` 均**不可写**（不是 ACL 写错，是沙箱层拦截）。`tools/gbuild.ps1`/`gbuild.cmd` 已固化解法：

1. `GRADLE_USER_HOME` 指工作区 `.gradle-home`；
2. **强制 `-Pkotlin.compiler.execution.strategy=in-process`**（否则 kotlin daemon 起不来：`AccessDeniedException ... kotlin-daemon-client-tsmarker` → `Could not connect to Kotlin compile daemon`）；
3. **不要加 `--offline`**：`.gradle-home` 里 jar 是齐的，但 `metadata-2.107` descriptor 索引不完整，offline 会误判「No cached version」（junit 尤其）；
4. 构建前清理不可覆盖的 `build/reports/problems/problems-report.html`；
5. 本机**没有 `pwsh`**（只有 Windows PowerShell 5.1），一律走 `tools\gbuild.cmd`；
6. 多 agent 并发构建会打坏 `caches/8.13/transforms` 的 `metadata.bin` → 报 `Could not read workspace metadata`。解法：`gradle --stop` + 结束 java 进程 + 删 `caches/8.13/transforms` 重建。

## 五、残留风险与未做项（诚实标注）

1. **未做真机验证**——全部观感结论来自模拟器 + 既有真机实测数据外推。玻璃 blur 相关（D1/D2、chromeScrim、透字）必须真机复测。
2. **浅色档无实测锚点**——取色拟合（ΔE00）与透字模型都只用深色锚点标定。浅色 `chromeScrim 0.74` 经复算属**过剩**（推算 1.05:1），有下调到 0.5 量级的空间，但本轮不动（深浅两档刻意同量级，避免切换时材质跳变），已在 `light()` 注释标注「待真机验证」。
3. **判据口径偏乐观**（如实标注，未推翻历史结论）：WCAG +0.05 常数项在暗部压缩比值，c=1.35:1 对应 sRGB 振幅 21.4，仍是可见调制。所以「c<2:1 = 不可辨」比字面更严。
4. **横屏未回归验证**——本轮播放页几何按竖屏重排，横屏双栏路径靠静态推理（封面仍由列高约束）；建议真机横屏补一轮。
5. **`EmptyState` 仅接入三处**，搜索无结果、播放队列空等仍是裸文本（已在空态组件 KDoc 记录清单），留待下一轮。
6. **`rowPressFeedback` 手感**静态截图无法验证，需触摸确认。
7. **播放模式合并的一个产品取舍**：牺牲「随机 + 单曲循环」组合（论证见 ⑤）。若后续产品要求恢复该组合，需要把按钮改回「主按钮 + 长按子菜单」而非四态环。
