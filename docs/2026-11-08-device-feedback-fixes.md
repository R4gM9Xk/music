## 二、逐项实现

### ① 封面尺寸：从「占满舞台」收回

**上一版算法**：`min(stageW − 2×20dp, stageH−预留−8%)`。在 411dp 屏上算出 **371dp = 屏宽的 90%**，把歌名组和玻璃控制台一起挤到屏幕底部，读起来是「一张图 + 一条尾巴」而不是「一张唱片 + 一套控制台」。

**问题诊断**：上一版把「取消 280dp 常量上限」当成了目标本身。但**比例推导**与**质量上限**是两件事——上一轮正确地取消了错误的常量，却连"内容本身的合理尺寸"一起否定了。

**新算法（三档取小）**：

```
bigSize = min(
  min(stageW × 0.82, stageW − 2×20dp),   // 宽度档：比例为主，边距兜底
  stageH − 纯音乐预留 − stageH × 0.16,     // 高度档：呼吸从 8% 提到 16%
  360dp                                    // 质量上限
)
```

各档理由：
- **0.82 比例**：留白随屏幕走是错的，**比例**才是跨机型稳定的构图关系。411dp 屏 → 337dp，两侧各余 ~37dp，形成「外向留白（37）> 内向留白（20，与歌名左边距同值）」的经典构图比例。
- **边距兜底**：保证不小于「屏宽 − 2×边距」，否则用户用手动分屏把窗口压到极窄时，封面会碎得比边距还小。
- **高度呼吸 16%**：8% 在 905dp 高的屏上只有 72dp，扣掉纯音乐预留后几乎不留白。
- **360dp 质量上限**：**这是本仓唯一允许的常量上限**。纯比例推导在平板/折叠屏上会让封面长到 600dp+，而唱片封面是**有视觉合理尺寸**的内容——超过约 360dp 后它不再"随屏幕变大而更清晰"，只是把同一张位图放大插值。**比例负责跨机型比例感，常量负责质量上限，两者取小才是完整表达式**。

> 这也修正了上一轮 KDoc 里「不含任何常量上限」这句已经变成错的话（已改）。

### ② 控制行排版：`SpaceBetween` 是错的容器

**逐像素实测**（411dp 屏截图）：
```
模式钮图标中心 13.8% ｜ 上一首 29% ｜ 播放 50% ｜ 下一首 71% ｜ 右侧空
```
左右**不对称**——左边有个真实控件、右边是个空 Spacer。`SpaceBetween` 均分的是**剩余空间**，5 个宽度不等的子项被均分后，播放键与两侧相邻项的**缝隙**并不相等。肉眼读作「播放键偏右、左边挤了个模式钮」。

**修法：三段等权重**
```
[ 左段 weight(1f)，模式钮居中右对齐 ] [ 中段：上一首·播放·下一首，spacedBy(16dp) ] [ 右段 weight(1f) 留白 ]
```
- 两侧等权重 → 播放键**恒在屏幕正中**，与下方进度条严格对齐；
- 中段用 `spacedBy` 而非 `SpaceBetween` → 播放键两侧缝隙**显式相等**；
- 右段刻意留空：它不是"待填的坑"，而是让左段模式钮有对手的**配重**——不对称排布永远读作错位，除非两侧都有内容。

### ③ 导航栏过黑：不是模型算错，是模型没优化过的维度 ★

用户只反馈了**导航栏**，迷你条没有意见。两者 `scrim` 原本相同，差异在填充档：

| | 填充 | 高度 | 反馈 |
|---|---|---|---|
| 迷你条 | `Hi`（白 16%） | 62dp | 无 |
| 导航栏 | `Md`（白 10%） | 58dp | **太黑** |

少了 6 个百分点白填充，叠在同一个深 scrim 上，读起来明显更黑。**所以根因不是 scrim 值，而是两块同级 chrome 的材质等级错配。**

**但更深一层**：`chromeScrim` 0.80 是「透字不可辨」这条**下界**的最省事取值，它从未约束**上界**——玻璃还剩多少通透感。这是原推导的盲区：**只优化了一个方向**。

**修法两步（缺一不可）**：
1. 导航栏填充 `Md` → `Hi`、blur 20 → 26dp：**这是纠错**，两块悬浮 chrome 本该同级（旧 `Md` 是当初"导航不如迷你条重要"随手拍的，无依据）；
2. 新增 `GlassColors.chromeScrimNav`，导航栏 0.80 → **0.72**（深色）/ 0.74 → **0.66**（浅色）：**这一步才是有意放宽下界**。

**放宽的代价（如实标注）**：退化路径（无 RenderEffect，blur 完全不生效）下导航栏透字对比 1.82 → 约 **2.1:1**。对照：导航栏自身文字 11.8:1、清晰文字 18:1。2.1:1 读作「雾里的轮廓」而非「能读的字」，仍远在可辨之下，但**不再是"几乎不可见"**。

**边界**：
- **迷你条继续 0.80**：它没被反馈，且更高更显眼，保持最严一档没有代价。
- 0.72 是**实测前的推测**。真机上若列表文字开始可读，回退 0.76（模型下限 0.772，刻意不取临界值）。
- `lerpGlassColors` 已同步新字段（漏了会让主题切换瞬间回落成深色黑板，这是既有 KDoc 记录过的坑）。

### ④ 设置页：模态面板 → 行内下拉

**改前**：玻璃强度/动效强度点开 `ModalSheet` 面板，列三档、当前档高亮。

**改后**：行尾一枚胶囊 `当前值 ⌄`，点它原地展开短列表，选中项右侧**蓝色对勾**（用 `auroraAccentColor()`，随取色变化）。

**为什么这不只是审美偏好**——两种形态的成本差是结构性的：

| | 模态面板 | 行内下拉 |
|---|---|---|
| 转场 | 整屏变暗 + 底部滑出 + 选完滑回（2 次动画） | 零 |
| 上下文 | 打开期间看不到自己在改哪一行 | 原地可见 |
| 适合 | 多项、需要确认、需要上下文 | **三选一、即时生效** |

三档这种量级，模态的仪式感是纯开销。这也与用户参照的系统设置语言一致。

**为什么不用 Material `DropdownMenu`**：本 App 弹层语言是液态玻璃（GlassSurface + haze + 描边 + 顶线），Material 自带 Surface 填充与阴影，材质对不上——会浮出一块"不属于这个 App 的白板"。这里用 `Popup` + 自绘玻璃容器，与 `ModalSheet` 同一材质来源。

**新增 `SettingDropdown.kt`**（约 250 行）要点：
- **触发器**是胶囊，不是整行——整行点击留给真正需要跳转的行，职责分离，避免误触；
- 箭头 `ChevronUpDown` 展开时 180° 翻转（`graphicsLayer` 绘制期读，不新增布局节点），时长走 `tweenHover`；
- 列表项 `role = Role.RadioButton` + `selected` 语义（**单选**不是普通按钮）；
- 未选中项保留等宽 18dp 占位——否则选中项多出图标会把文字挤窄，三行左缘错位；
- `Popup(focusable = true)` 点外部关闭，无「确定」——单选没有可失败的提交；
- 新增两枚图标 `Check`（对勾）/ `ChevronUpDown`（上下尖角，与 `ChevronRight` 的"进入下一页"语义分工明确）。

## 四、残留风险

1. **②③ 未经真机确认**——数值推导可靠，但"看起来对不对"只有真机能答。
2. **`chromeScrimNav` 的 0.72 是推测上限**，模型给出的边界是 0.772。若真机上列表文字变可读，回退 0.76。
3. **迷你条与导航栏 scrim 不再同值**（0.80 vs 0.72）——这是有意的分档，但两者在飞行替身中会交接：`PlayerFlightOverlay` 的 `lerp(glass.chromeScrim, Transparent, t)` 用的是迷你条的 0.80（正确，飞行起点是迷你条），落地到导航栏时无替身参与，不影响。
4. 360dp 质量上限对平板/折叠屏未经实测（本项目目标机型为手机）。
